Operating Systems Architecture Deep-Dive · HDFS & GFS Principles

Distributed File System (DFS) Simulator & Management Dashboard

An interactive guide to how large distributed systems (like Google File System & Apache Hadoop) store, protect, and self-heal files across multiple servers.

How Distributed Storage Works (In Simple Terms)

On a regular computer, a file lives on a single hard drive. If that disk crashes or the machine loses power, the file is lost or inaccessible.

In a Distributed File System (like Google File System or Apache HDFS), large files are sliced into smaller blocks (chunks) and stored on multiple physical servers across separate server racks (Rack-Alpha & Rack-Beta). A central coordinator (NameNode) keeps track of everything. Even if an entire server crashes or a power switch fails, your files stay 100% safe, accessible, and automatically self-healed from backup copies.

How the System Works Step-by-Step (dfsEngine.ts)

STEP 01

Splitting Files into Chunks & Checking Integrity

File Partitioning

When you upload a file, the system cuts it into smaller 512 KB blocks. Each block gets a unique hash (checksum) so any file corruption or transmission error is caught immediately.

STEP 02

Saving Copies Across Different Racks (Rack Awareness)

Fault Domains

Every block is copied 2 to 3 times and stored across separate server racks (Rack-Alpha & Rack-Beta). If an entire rack loses power or a network switch fails, your files remain completely safe on another rack.

STEP 03

Master Coordinator & Worker Storage Nodes

Inode Separation

The Master (NameNode) tracks where each block lives using an Inode table, while Worker Nodes (DataNodes) actually store the data blocks and send heartbeats every 3 seconds to confirm they are online.

STEP 04

Simulating Server Crashes & Quorum Health

High Availability

You can simulate server crashes anytime by switching nodes Offline with the live power buttons. Your files still open and download smoothly as long as at least one copy is alive, while a strict >50% majority quorum protects data integrity.

STEP 05

Automatic Self-Healing & Disk Balancing

Self-Repair & Load Leveling

If a server goes down for good, clicking Self-Heal automatically copies the missing chunks onto healthy servers. The Rebalance button then spreads the storage load evenly so no single disk gets overloaded.

Operating Systems (OS) Concepts Implemented

1. Inode Architecture

OS: Linux/Unix ext4 Inode table separated from data blocks

NameNode maintains a centralized Inode table. When a user requests a file, the NameNode delivers block location pointers (IPs & chunk IDs) rather than streaming raw disk data.

2. Block-Level Chunking

OS: Fixed 4KB disk sectors avoiding internal fragmentation

Large files are partitioned into uniform 512 KB logical chunks. This allows a 100 GB file to be concurrently distributed across four 25 GB storage nodes with zero waste.

3. Distributed RAID Redundancy

OS: RAID-1 / RAID-5 disk mirroring across physical disks

Multi-replica redundancy (2x/3x) stores copies across distinct physical servers, guaranteeing zero data loss even during hardware motherboard or disk failures.

4. Heartbeat & Liveness Probing

OS: Kernel watchdog timer & process hang monitoring

Every DataNode sends a periodic 3000ms heartbeat to the NameNode coordinator. Missed heartbeats instantly flag the node as offline and initiate failover.

5. Quorum Consensus

OS: Distributed mutex & consensus protocols (Paxos / Raft)

Cluster requires a strict >50% majority quorum (Nodes/2 + 1). If majority nodes drop offline, cluster enters safe degraded mode to eliminate split-brain data corruption.

6. Rack Awareness & Failure Zones

OS: Fault isolation domains in high-availability clusters

DataNodes are segregated into Rack-Alpha and Rack-Beta. Chunk replicas are intentionally placed on alternate racks to survive full rack power switch disconnections.

7. Self-Healing & Disk Rebalancing

OS: Autonomic computing, garbage collection, and disk defragmentation

Under-replicated chunks from crashed servers are automatically re-cloned to healthy nodes. The cluster rebalance algorithm minimizes storage variance across disks to prevent hot-spot exhaustion.
